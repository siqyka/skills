# Handoff 模板（完整字段版）

复制下面骨架，逐个字段填**具体值**。填不出来的字段直接删掉，不要留 `TODO` 或 `{}`。

```markdown
# Handoff — <主题，一句话>

> 生成时间：<ISO 8601 带时区>　｜　来源会话：<session id，或 "当前会话 / lead">　｜　交接目的：<下一个会话要干什么，一句话>

## 0. 元信息

| 字段 | 值 |
|---|---|
| 工作区绝对路径 | `<绝对路径>` |
| git 分支 / HEAD | `<branch>` @ `<短 commit>` |
| 未提交改动 | `<N> 个文件：<清单>`（说明是否可回滚） |
| 权限模式 | `workspace-write` / `danger-full-access`；是否需要审批 |
| 目标 id / 状态 | `goal <id>`（active）/ 无 |
| 后台作业 | `job-<id>`（用途 + 端口）/ 无 |
| 端口转发 / 远端挂载 | `localhost:<port>` → 远端 `<port>`（转发 id）/ `ssh://<host>/<path>` / 无 |
| 环境依赖 | Python/Node 版本、需要的 MCP 或 CLI、已装 skill |
| 临时文件（待清理） | `<本次交接产生的绝对路径>`（作用）/ 无 |
| 未覆盖区间 | `<blockId / 消息范围>`（判过但无残留）/ 无 |

> 「临时文件」只列本次为交接而新建的东西（本文件自身、临时脚本、中间导出、缓冲目录）；
> 用户产物与第 6 节「引用清单」里的交付物不属于临时文件，不要写进来。
> 接手方读完文档、动手前，按此清单用选择弹窗询问是否删除；写 handoff 的生成端只登记、不问也不删。

## 1. 目标

- **要达成什么**：<可验收的一句>
- **为什么**：<动机，决定了取舍方向>
- **明确不做**：<防止接收方扩范围的事项>
- **目标演进**：（若中途变过）<最初要 A → 后来改成 B — 因为 C>

## 2. 已确认事实（接收方不必再验证）

**从头覆盖到现在**，不要只写最近几轮。可选但推荐加一张时间线，然后再列细节：

| 段（ref / blockId） | 需求或目标变化 | 确认的事实 | 决策 + 理由 | 排除 / 失败 |
|---|---|---|---|---|
| 会话开头 | <原始诉求> | <…> | <…> | <…> |
| 中段 | <…> | <…> | <…> | <…> |
| 最近 | <…> | <…> | <…> | <…> |

细节条目：

- `<结论>` — 依据：`<命令输出 / 文件:行号 / URL>`
- 决策：<选 X 不选 Y> — 理由：<Z>
- <已跑通的命令与真实输出摘要>
- <还没有结论、但已经排除的方向>（含为什么排除）

## 3. 下一步最小行动

按顺序，每条都能直接执行：

1. `<path:line>` — <具体改什么 / 跑什么>
2. `<命令>`（在 `<绝对目录>` 下执行）— <预期会看到什么>
3. …

> 最后一条应指向「验收」，让接手者知道何时可以停。

## 4. 陷阱与禁区

- **已踩的坑**：<现象 + 报错原文，原样保留，能 grep 到>
- **不能碰**：<生成文件 / 迁移 / 线上配置 / 用户未授权目录>
- **失败的尝试**：<试过什么，为什么不行>

## 5. 验收标准

- [ ] `<命令>` → 预期输出 `<精确文字或断言>`
- [ ] 可观察行为：<打开某页面 / 某接口返回某结构>
- [ ] 回归项：<不能弄坏的东西>

## 6. 引用清单（只给位置，不复制内容）

| 类型 | 位置 | 说明 |
|---|---|---|
| 产物 | `<绝对路径>` | <是什么> |
| 规格 / 计划 | `<绝对路径或 URL>` | <需要看哪一节> |
| 外部资料 | `<URL>` | <可信度备注> |

## 7. 建议使用的 skill 与工具

- skill：`<精确名字>` — <用在哪一步>（名字必须真实存在于当前 skill 目录）
- 工具 / 命令：<关键 CLI 或 MCP 调用>

## 8. 审查发现（仅审查/审计场景）

| # | 问题 | 严重度 | 涉及文件（绝对路径） | 建议处理 |
|---|---|---|---|---|
| 1 | <现象 + 影响> | 高/中/低 | `<绝对路径:行>` | <改法> |

### 已修复

- <本轮直接改掉的>

### 遗留

- <需要后续会话处理，附原因>

- 整体判断：<可用 / 有条件可用 / 需返工>

```

## 字段填写规则

| 字段 | 规则 |
|---|---|
| 元信息 | 只写会导致接手者踩坑的项；没用到就删行，不要留「无」 |
| 未覆盖区间 | 判过却没抽出东西的压缩块写在这里；空白 = 你声称已覆盖全部，别撒谎 |
| 目标 | 「明确不做」比「要做什么」更能防止跑偏，必填；目标变过就写演进路径 |
| 已确认事实 | 必须带依据；不带依据的判断降级成「假设」并标出来。**从会话第一轮写到现在**，只写后几轮等于没交接 |
| 下一步 | 禁止「优化性能」「完善一下」这类动词；每条都要能被下一个人直接开工 |
| 陷阱 | 报错原文照抄，不要转述成「报了个错」 |
| 验收 | 至少一条是命令 + 预期输出，否则不算验收 |
| 引用 | 绝对路径或完整 URL；同一产物只出现一次 |
| 临时文件 | 只列本次交接产生的；宁可多登记一条，也不要让文件变成没人认领的垃圾 |
| skill | 名字照抄当前目录里的实际名，别自己造 |

## 长度控制

- 目标 100–200 行。
- 超过 300 行：说明你把本该外置的产物（报告、清单、diff）搬进了文档，挪出去、留路径。
- 少于 40 行：要么任务真的很小，要么你漏了「陷阱」或「验收」。
